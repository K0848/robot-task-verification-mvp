## 总体判断

V2 的范围已经明显收敛：单机器人、单抓放任务、两版参数策略、运行记录、回放、比较和报告，适合作为具身智能产品工程求职作品。

当前 PRD 还不能直接指导实现。主要问题不是方向错误，而是实时执行、Windows 依赖、V1/V2 数据契约和动作展示之间存在未解决的工程边界。

## P0 必须修复

### 1. 实时仿真与 Streamlit 解耦

物理仿真不能在 Streamlit 页面进程内高频步进。V2 的“实时”应定义为：后台或子进程执行仿真，平台轮询 queued、running、finished 状态，运行结束后加载轨迹和报告。

前端不负责动力学循环；首阶段不做高频物理状态推流或网页实时控制。

### 2. Windows 环境风险

当前电脑是 Windows 11、Python 3.12、32GB 内存、Intel 集成显卡、无 NVIDIA CUDA。robosuite 可能受到 Python、离屏渲染和依赖兼容影响。

实现前必须准备替代路径：优先验证原生 MuJoCo Python 绑定和极简自定义 XML；若 robosuite 可稳定安装则使用 PickPlaceSingle；若原生 Windows 失败则使用 WSL2/Linux 作为仿真执行环境，平台继续运行在本机。

### 3. 明确 V1 与 V2 的数据边界

V1 的 data/store.json 和预设运行数据不能继续作为 V2 物理运行的唯一存储。V2 至少要区分运行元数据、运行轨迹和视频/仿真日志等原始产物。

V1 的强制推荐某个版本规则也不能覆盖 V2 的“证据不足，需要补测”状态。

### 4. 物理轨迹与 Three.js 展示一致

如果 V2 宣称运行了物理仿真，前端不能只显示与真实机械臂无关的三轴玩具模型和 snap 跳变。

首阶段需要读取仿真轨迹并按同一坐标定义回放，或者明确标注为抽象轨迹展示，不宣称是物理机械臂的真实几何回放。物体位置不能继续用预设 snap 规则代替物理运行记录。

## P1 建议修复

- 给成功判定写出可执行阈值，并明确结束状态不等于成功；
- 保存环境版本、初始状态快照和必要的动力学状态，而不是只保存随机种子；
- 两版策略只允许改变一个明确参数；
- 轨迹文件按运行拆分，store.json 只保存轻量索引；
- 用户访谈和独立试用作为增强证据，不作为求职作品进入实现的硬门槛；
- 将失败报告固定为“观察事实 → 失败分类 → 可能原因 → 下一步补测”。

## 保留项

- 单机械臂、单抓放任务的极简切片；
- 排除 VLA 训练、多机器人、多任务、云端部署和大规模数据集；
- “证据不足，需要补测”的结论状态；
- 失败观察与原因推断分层；
- CPU 优先、普通电脑可复现的目标。

## 最小可执行验收

1. 一个仿真任务可以在独立进程中运行；
2. 平台不会因仿真运行而卡死；
3. 运行产物包含时间戳、动作或位姿、物体状态、事件和结果；
4. 成功判定使用明确阈值；
5. 两个参数版本使用相同初始状态进行比较；
6. 平台能加载真实轨迹并回放；
7. 报告能区分成功、失败、未知和证据不足；
8. README 能说明本机依赖、运行命令和已知限制。
