# 接口与数据契约

> 版本 v2.0 · 2026-09-22

本文档记录当前模块之间可依赖的调用和数据规则。当前项目没有 HTTP API；这里的“接口”包括 `JsonStore` 的 Python 调用面、`data/store.json` 持久化结构，以及 Python 到 Three.js 的 `RendererPayload` 协议。

## 1. 契约原则

- Python 侧是运行结果和业务规则的唯一事实来源。
- 所有时间统一使用 ISO 8601 字符串；持续时间和偏移量统一使用毫秒整数。
- 状态、场景、动画模式和动态配置使用固定枚举值；展示文案可以变化，机器判断依赖 ID/枚举值。
- `RendererPayload` 只读传递给前端；前端不能写回运行结果。
- 新增字段优先向后兼容：读取时允许缺省，写入时只新增必要字段；改变字段含义时必须升级契约版本或提供迁移。

## 2. JsonStore 调用面

| 方法 | 输入 | 输出 | 主要行为 |
|---|---|---|---|
| `ensure_bootstrap()` | 无 | `None` | 文件不存在时创建种子数据 |
| `load()` | 无 | `StoreData` | 读取 JSON、反序列化，并同步默认字段 |
| `save(data)` | `StoreData` | `None` | 将完整数据集格式化写回 JSON |
| `sync_running_runs()` | 无 | `StoreData` | 同步已经到期的运行状态 |
| `create_live_run(...)` | 任务、策略、预设、备注及可选动态配置 | `run_id: str` | 创建运行、事件和回放帧并持久化 |
| `create_benchmark_batch(...)` | 任务、策略、评测套件、备注 | `batch_id: str` | 批量创建运行和评测批次并持久化 |
| `get_run_bundle(run_id)` | 运行 ID | `(RunRecord | None, RunEvent[], ReplayFrame[])` | 返回运行及其关联事件、帧 |

调用约束：

- `task_template_id`、`strategy_version_id`、`suite_id` 必须存在于当前 `StoreData`；当前实现对未知 ID 使用查找失败，调用方应在页面层先从已有选项中选择。
- 创建运行和创建评测批次是完整写入操作，返回 ID 前必须已经写入运行记录、事件和帧。
- `get_run_bundle()` 会先同步运行状态，因此读取可能触发一次本地 JSON 更新。
- 当前没有并发锁、幂等键或事务回滚；它的适用范围是单用户本地演示。

## 3. `store.json` 顶层契约

```json
{
  "task_templates": [],
  "strategy_versions": [],
  "benchmark_suites": [],
  "benchmark_batches": [],
  "run_records": [],
  "run_events": [],
  "replay_frames": []
}
```

顶层集合及关联关系：

| 集合 | 关键关系 | 说明 |
|---|---|---|
| `task_templates` | `RunRecord.task_template_id` | 任务定义和成功标准 |
| `strategy_versions` | `RunRecord.strategy_version_id` | 策略版本定义 |
| `benchmark_suites` | `BenchmarkBatch.suite_id` | 用例集合和关注指标 |
| `benchmark_batches` | `run_ids[]` | 一轮批量评测及其运行 ID |
| `run_records` | `id` | 单次运行主记录 |
| `run_events` | `run_id` | 时间线事件 |
| `replay_frames` | `run_id` | 动作回放帧 |

## 4. 运行记录字段规则

### `RunRecord`

| 字段 | 类型 | 规则 |
|---|---|---|
| `id` | string | 运行唯一标识 |
| `task_template_id` | string | 必须关联任务模板 |
| `strategy_version_id` | string | 必须关联策略版本 |
| `status` | enum | `queued` / `running` / `succeeded` / `failed` / `cancelled` |
| `started_at` | ISO 8601 string | 运行开始时间 |
| `ended_at` | ISO 8601 string | 预计或实际结束时间 |
| `duration_ms` | integer | 非负，总时长 |
| `result` | object | 见 `RunResult` |
| `input_params` | object | 输入、解析结果和评测元数据；当前允许扩展 |
| `tags` | string[] | 用于筛选，例如 `benchmark-generated` |

### `RunResult`

| 字段 | 类型 | 规则 |
|---|---|---|
| `success` | boolean | 与最终业务结果一致 |
| `final_status` | enum | 应与运行最终状态一致 |
| `failure_reason` | string/null | 成功时通常为空，失败时应可解释 |
| `key_observation` | string | 面向用户的关键观察 |
| `quality_score` | number | 当前为模拟质量分 |
| `notes` | string | 建议或补充说明 |
| `scenario_label` | string | 场景展示名称 |
| `operator_note` | string/null | 用户输入备注 |

### `RunEvent` 与 `ReplayFrame`

事件必须包含 `run_id`、`offset_ms`、`stage`、`level`、`message`；回放帧必须包含 `run_id`、`offset_ms`、`stage`、`arm_pose`、`gripper_state`、`target_state`。同一运行的事件和帧必须使用相同的运行 ID，偏移量必须落在 `[0, duration_ms]` 范围内并按时间顺序生成。

## 5. `RendererPayload` 契约

Python 的 `build_renderer_payload()` 输出以下结构：

```json
{
  "view_mode": "detail",
  "title": "实时任务状态",
  "compare_label": null,
  "status": "running",
  "success": true,
  "scenario_label": "标准成功",
  "resolved_scenario": "success",
  "progress": 0.68,
  "current_stage": "转运中",
  "highlight_mode": "overview",
  "camera_preset": "sim-isometric",
  "dynamic_profile": {
    "pace": "default",
    "pace_multiplier": 1.0,
    "focus": "overview",
    "matched_keywords": []
  },
  "scene": {
    "object_label": "阀门盖",
    "source_bin": "B1",
    "target_slot": "Tray-01",
    "surface": ""
  },
  "animation": {
    "mode": "live",
    "duration_ms": 42000,
    "initial_elapsed_ms": 28560
  },
  "frames": [],
  "events": []
}
```

字段规则：

| 字段 | 允许值/类型 | 约束 |
|---|---|---|
| `view_mode` | string | 当前页面使用 `preview`、`detail`、`replay`、`compare` |
| `status` | 运行状态枚举 | 与运行记录状态一致 |
| `success` | boolean | 与 `RunResult.success` 一致 |
| `progress` | number | 应在 `0..1` |
| `highlight_mode` | `overview` / `grasp` / `place` / `failure` | 对应动态聚焦模式 |
| `animation.mode` | `loop` / `live` / `static` | 预览循环、运行实时、回放/对比静态 |
| `animation.duration_ms` | non-negative integer | 与运行总时长一致 |
| `animation.initial_elapsed_ms` | non-negative integer | 应不超过总时长；loop 模式可取模 |
| `frames` | `FramePayload[]` | 至少一个有效帧才能渲染动作 |
| `events` | `EventPayload[]` | 用于时间线和失败时刻定位 |

前端 `payload.ts` 负责归一化动态配置、时间计算和帧采样；它可以对缺省动态配置使用默认值，但不能修正业务状态、成功结果或失败原因。

## 6. 动态配置规则

| 配置 | 值 | 当前来源 |
|---|---|---|
| 节奏 | `default` / `fast` / `slow` | 策略默认值或备注关键词 |
| 倍速 | `1.0` / `1.35` / `0.70` | 与节奏绑定，可由备注覆盖策略默认值 |
| 聚焦 | `overview` / `grasp` / `place` / `failure` | 备注关键词 |
| 关键词 | string[] | 仅记录实际匹配到的关键词 |

动态配置影响动作播放和镜头聚焦，不改变场景选择、运行成功与否或评测结论。

## 7. 兼容、错误与迁移

- 新增 JSON 字段时，`from_dict()` 应提供默认值，旧 `store.json` 可以继续加载。
- 删除或重命名字段前，必须提供迁移逻辑并更新测试；不能依赖手动修改本地运行数据。
- 改变枚举含义时，应新增枚举值或契约版本，不能复用旧值表达新语义。
- 运行记录缺少事件或帧时，页面应显示可理解的缺失提示；不能把缺失数据当成成功运行。
- Three.js 无法渲染时使用 SVG 回退；这属于展示层错误，不应被记录为任务失败。
- 当前 JSON 写入失败、未知 ID 和非法结构会直接抛出异常；如果未来接入真实用户或外部数据，需要在边界层转换为结构化错误并增加恢复策略。

## 8. 变更检查清单

涉及以下任一变更时，必须同步本文件：

- `models.py` 的字段、序列化或反序列化规则；
- `JsonStore` 方法签名、写入时机或错误行为；
- `build_renderer_payload()` 的字段；
- `payload.ts` 的类型、枚举、采样和插值规则；
- 状态机、场景 ID、策略 ID 或 benchmark case ID；
- `input_params` 中被多个页面或模块依赖的字段。

## 9. V2 运行产物契约

> 本节描述旧平面任务 `v2.0`。Panda 完整模型增量使用 `v2.1`，见第 13 节。不能假定旧 artifact 含有关节/完整几何字段，不能用旧成功阈值解释 Panda。

V2 不复用 `data/store.json` 作为物理运行的事实存储。每次运行使用独立目录 `data/v2_runs/<run_id>/`，目录内文件如下：

| 文件 | 所有者 | 规则 |
|---|---|---|
| `config.json` | JobManager | 固化策略 ID、唯一变化参数、初始条件、故障注入和 run ID |
| `meta.json` | physics runner | 固化环境版本、模型名、Python/平台、初始 `qpos/qvel`、轨迹来源 |
| `status.json` | worker / JobManager | `queued/running/succeeded/failed`；必须包含阶段、进度、更新时间；父进程负责 timeout/crash 转换 |
| `trajectory.jsonl` | physics runner | 每行一帧，包含 `step`、仿真时间、阶段、工具/物体/目标三维坐标、夹爪状态、约束状态、`qpos/qvel` |
| `events.jsonl` | physics runner | 每行事件，包含 run ID、偏移量、阶段、级别和消息 |
| `summary.json` | physics runner | 基于实际最终帧计算的成功结果、阈值、样本量、失败分层和证据范围 |

状态语义：`queued` 表示目录已创建但 worker 未开始；`running` 表示至少产生了一次状态更新；`succeeded`/`failed` 是终态。`done` 或进程退出不能直接当作任务成功。

成功判定当前固定为：`grasp_locked=true`、已释放、释放后物体到目标中心的二维距离不超过 `0.08m`，且最终物体高度不低于 `0.025m`。阈值必须与 summary 一起保存；它只适用于当前轻量 MuJoCo 模型。

## 10. V2 比较与展示契约

`build_comparison_report()` 只接受至少两份不同且已完成的物理运行。完整性和可比性先于统计；同模型/初态/评估口径下仅允许指定参数变化。当前固定条件样本统一保留 `evidence_insufficient`（不足以外推泛化），不再以累计3次自动升级证据。重复性检查与参数比较分别标识，详见第14节。

`artifact_to_renderer_payload()` 的 `frames` 直接来自 `trajectory.jsonl`；必须携带 `trajectory_source=mujoco-runtime` 和 `coordinate_system=mujoco-world`。每帧的工具、物体和目标位置包含 MuJoCo 的 x/y/z 坐标。Three.js 在该坐标系下只做比例/轴向转换，不添加 V1 的抬升弧线、物体 snap 或失败抖动；V1 payload 继续使用 `legacy-scene` 分支。该 payload 是只读展示数据，不可反写运行结果，也不能混入 V1 的预设场景字段作为物理证据。

## 11. V2 错误契约

| 错误 | 产生者 | 对外表现 |
|---|---|---|
| `worker_exception` | worker | status=failed，保留 `error.log` 和错误消息 |
| `worker_crash` | JobManager | status=failed，保留 stderr 片段 |
| `timeout` | JobManager | 终止 worker，status=failed，页面不阻塞 |
| 缺少 artifact | adapter | 明确报错，不降级为 V1 演示数据 |

## 12. V2 与 TC-01～TC-05 追踪

### 可视化修复后的实际调用边界（2026-09-22）

- V2 页面通过 `v2_view.render_evidence()` → bundle `renderPhysical()`，不调用 V1 `render_motion_scene()`、`sampleFrame()` 或 `build_svg_scene_html()`；V1 分支不变。
- 回放的时间、暂停、倍速、事件选中与视图模式由浏览器组件拥有。两种渲染器共用 `samplePhysicalFrame()`：位置线性插值，阶段/夹爪/held/placed 在下一记录点才切换；帧源不变。
- Three.js 使用 `[x,z,-y]` 轴转换保持右手系；SVG 使用 X–Z 侧视投影（Y 值在数值栏显示），不把工具和物体吸附。前端只显示位置示意，物体朝向固定，绝不宣称重建真实机器人关节或物体旋转。
- 后端终态由 status 文件决定；回放 0% 仅表示当前查看首帧，不代表 worker 未完成。页面分别显示执行状态与回放秒数。
- 轮询 fragment 只在 queued/running 挂载，终态触发一次整页重跑恢复启动/清除按钮，之后不定时重建回放。进程退出后 poll 回收管道句柄。
- 手动渲染切换会暂停并保留时刻；WebGL 初始化失败/上下文丢失自动回退到同一时间点的 SVG。JS bundle 缺失时明确提示构建命令，报告仍可查看，不假装完整回放可用。
- 报告按 observation/classification/possible_cause/unknown 展示，结论来源仍是 summary；原始 JSON 和环境可展开并下载报告。

| 验收案例 | 主要契约/入口 |
|---|---|
| TC-01 | `v2_cli run --strategy baseline`、运行目录六文件 |
| TC-02 | `--grasp-offset 0.08`、summary.failure 分层 |
| TC-03 | `--fault crash/timeout`、status.error_code |
| TC-04 | `v2_cli compare`、同初始状态/唯一差异/证据不足 |
| TC-05 | `v2_adapter.artifact_to_renderer_payload`、真实 trajectory |

## 13. Panda v2.1 与完整几何回放

Panda 的 `model_id=panda-cube-v1`，默认 7000 个 .002s 物理步，共 14s 仿真；时间记录为实际 `data.time` 换算毫秒。CLI 不指定模型仍使用旧平面；网页默认 Panda。运行参数在创建 worker 前校验，run ID 必须是安全目录名，数值不能为字符串、布尔或非有限值。

| 产物 | Panda 增量字段/行为 |
|---|---|
| `meta.json` | `artifact_schema=v2.1`、`model`（来源/模型hash/场景）、`scene_sha256`、控制器版本、完整评估参数、初始 qpos/qvel/ctrl/time 与数据来源 |
| `scene.json` | `schema=panda-scene-1`；网格以 base64 编码 little-endian float32 顶点/uint32 索引；几何含 ID、body、类型、mesh ID、size、RGBA |
| `trajectory.jsonl` | `sim_time_ms` 严格递增；包含 qpos/qvel/ctrl、工具/物体/目标、物体朝向、实际夹爪开度、双指接触法向力、抬升/释放/稳定区间、与 scene 同顺序的 `geom_poses` |
| `geom_poses` | 每个可视几何的世界 position[3] 和 quaternion[4]，四元数为 wxyz；使用编译后顶点，不再施加第二次网格重心/缩放修正 |
| `summary.json` | 根据每物理步的接触与运动判据生成，而非仅末帧；保存阈值版本、抬升/释放状态、最后连续稳定时长、实际目标距离及失败分层 |
| `performance.json` | 模型加载/墙钟执行/仿真时间、记录帧数、进程峰值工作集和产物体积；测试进程与独立 worker 的统计口径必须注明 |

判据由 `panda_model.CRITERIA` 固定：物体离支撑面 .04m、双指接触支撑持续 .25s；夹爪实际间距达到 .06m 且双指脱离才记释放；物体在目标中心 .04m 内、支撑高度误差≤.01m、线速度≤.03m/s、角速度≤.2rad/s 持续 .5s 才稳定。它是本项目受控仿真条件，不是真机精度承诺。

`artifact_to_renderer_payload()` 的 Panda 附加字段为 `run_id`、`model_id`、`robot_scene`（上述 scene）、`robot_frames`（原始轨迹行）。`frames` 仍提供同源工具/物体位置；`held` 使用双指接触证据，不读取旧 `grasp_locked`；`placed` 使用该时刻的稳定时长，不因最终成功提前显示已放置。

前端用同一帧更新所有部件、状态和数字，取不晚于回放游标的最近记录帧；首帧前显示首条记录，并显示实际采样时间。MuJoCo 世界整体绕 X 轴 -90°，同时处理位置和朝向。`__ROBOT_DEBUG__()` 只读实际 Three.js 对象世界变换用于验证，不重新赋值姿态，不能影响业务状态。

拒绝回放：未知版本、scene内容哈希/模型身份错配、运行ID不一致、缺网格/几何姿态、非法数值或四元数、时间非单调/越界/末帧与时长不符。报告独立可读不表示已与损坏轨迹核对；页面必须明确标记此限制。

比较按模型 hash、scene hash、评估/控制器版本、初始状态与受控参数检查；唯一允许的参数差异是 `grasp_offset`。Panda 身份字段缺失、meta/summary 串运行、非法 success 等应拒绝优劣结论。保留原比较字段并增加 `comparison_status`、`identity_differences`、`strategy_groups`、`generalization_supported=false`。

生命周期：CLI `wait()` 和页面 `poll()` 均有墙钟期限；任务失败不同于 worker 异常；进程异常、无终态、墙钟超时分别保留错误原因，并在返回终态前完成进程/管道回收。诊断模式环境变量 `ROBOTS_ENABLE_FAULT_TESTS=1` 才显示 crash/timeout 注入，不属于正常策略评测。

## 14. V2 统一业务服务

`robot_mvp.v2_service.V2RunService` 是当前页面和CLI查询的入口；它不读取V1的`store.json`。未新增HTTP、数据库、取消/删除API或跨进程调度。模型与参数方案从`models()/presets()`获取，`start_run(preset_id, model_id=...)`集中创建参数，进程/超时仍委托既有JobManager。

| 接口 | 输入与默认 | 输出/约束 |
|---|---|---|
| `list_runs` | 默认Panda；model_id、status、include_diagnostics=False、limit=50、offset=0 | items/total/limit/offset/has_more/issues；limit为1～200；只轻量校验元数据，`validation_level=metadata_only` |
| `get_run` | run_id；validate_evidence=True | 无需JobHandle的历史详情；状态、任务结果、完整性、错误、报告可用性与参数分开返回；不存在抛FileNotFoundError，越界ID拒绝 |
| `replay_payload` | run_id | 先检查记录身份/终态，再复用实际artifact adapter校验/生成回放；不使用V1帧或填造缺失数据 |
| `suggest_comparison` | 默认Panda | 建议一条真实基线与同条件不同参数运行；校验候选真实产物；缺少合适pair返回空列表与原因，不默认最近两条 |
| `compare` | 至少2个run_id | 完整性→可比性→按实际参数分组；跨模型、重复run、非受控差异、坏证据拒绝 |
| `overview` | 默认Panda | 对指定模型完整验证后汇总；有效任务结果、未知、损坏、执行异常分别计数；无有效分母时task_success_rate=null |

详情 `integrity`：`pending`=记录为queued/running；`metadata_only`=轻量字段有效但尚未核对完整证据；`verified`=本次完整校验通过；`invalid`=损坏或冲突；`unavailable`=执行异常等导致没有有效任务报告。列表里的`task_success`只代表报告声明，须结合完整性；统计与比较不以metadata_only直接放行。

错误记录不静默跳过。无法归属模型/目录越界的项进入列表issues；可归属模型的坏记录留在items并附原因。显式crash/timeout诊断注入默认不进入正常查询与统计，真实执行错误（没有故障注入）仍保留。`process_liveness=not_observed`仅表示文件查询没有观察进程，不能把持久化running当作进程仍活着，也不能擅自改成failed。

创建时间优先meta.created_at；无meta的历史错误运行回退到配置文件修改时间或目录修改时间，`created_at_source`明确区分，不伪造精确创建字段。查询不修改原产物。

比较新增 `comparison_kind`：`repeatability_check`、`controlled_parameter_comparison`、`rejected`。`parameter_groups`按实际配置生成；同名不同参数分开，异名同参数合并；`strategy_groups`兼容原字段，名称碰撞附参数指纹。`generalization_supported`始终false。无效输入不计成功率（null），不输出强制推荐。

CLI新增 `list/show/overview`；查询默认Panda，`run`仍保留历史默认模型兼容。`compare`可比返回0，拒绝或参数错误返回2；结构化拒绝报告仍写stdout，不能把退出码0误当成拒绝也成功。
